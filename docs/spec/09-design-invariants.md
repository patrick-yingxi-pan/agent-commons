# 09 · Design invariants

> **Intent.** A handful of decisions are locked in — they shape every change and must
> not silently drift. Some are *form-follows-function* rules (logically parallel
> controls share one styled primitive, so a cue can't diverge between copies) and are
> each guarded by a dedicated test; others (token-driven theming, the IPv4 bind) are
> guarded structurally by the conformance test; a couple are review-enforced
> conventions, marked as such so the absence of an automated guard is explicit rather
> than assumed. (The scoped `CLAUDE.md` design decisions — `src/`, `server/`, `contract/`.)

| INV-9 | **Strict core, convenient edge — an absent request field must MEAN something, or be refused.** A write path never fills an absence by *choosing for the caller*: a field is either present and concrete, or absent with a fixed, documented semantic. The allowed absence classes: **inherit** (a session's unset provider pick = its Agent's — a read-time chain to a fixed root), **complete-set value default from fixed constants** (a confirmed create-provider op's effort levels / root authority), and **none — the minimal-risk meaning** (unset budget = no cap beyond the plan; unset instructions = `''`; unset agent `tools` = the **empty** set, never the catalog — the API never *widens* a grant silently; a Project with no `defaultRole` = no preference). Never allowed: resolving an absence to a **mutable entity or a privileged value** — a registry entry, a "current default", a role picked on the caller's behalf — because the write would mean something different later and the wiring bug would surface far from its cause; that class is refused (`ValidationError` → 400). Earned instances: the agent provider/prompt bindings (MODEL-15), the commission `role` (D14 — refused when unset; the Project's optional `defaultRole` is only what pickers pre-select), and the tool grant (explicit full-catalog, stated on the consent card). An INVALID value is refused the same way, never silently normalized (the old invalid-role→writer downgrade is gone). Conveniences that spare typing — pre-selections, defaults, label→id resolution — run at the **edge**, before the request or consent card, and their result is **shown** (the picker's selection; the create-agent card names its provider + prompt and states its tool grant; the commission card names its role; the CommissionAdd picker says what a click grants). Read-side the server may decorate with **computed, viewer-relative annotations** (`isDefault`, `online`, `own`) — never stored, stripped at every mint/patch funnel. **A viewer-relative CAPABILITY annotation must be computed by the very predicate the write path enforces** (2026-07-22 sweep): `Session.own`, `SocialCapability.canComment`/`canPropose`, `Discussion.canResolve`, `DiscussionPost.mine`/`canDelete`, `OpenSubGoal.canRetract` — each one shares its helper with the mutator that would refuse the act, so a control and the act behind it are one decision rather than two that happen to agree. Earned by both failure directions: a `view`-tier reader was offered a comment gutter on every turn (an affordance the wall refuses), and the thread page hid Resolve from the anchor owner while the entity panel showed it (a capability with no affordance). The corollary is a WIRE rule: when standing is decided from data the face deliberately redacts — work-item retract compares raw tenant ids because display names are attacker-controlled — the client *cannot* derive the gate and must be told, so the annotation is mandatory, not a convenience. When a new request field lands, classify its absence into one of the three classes or refuse it. | `server/conflict.ts` (`ValidationError`), `server/store/index.ts` (`createAgentFromRequest` / `updateAgentFromRequest` / `createCommission` / `setProjectDefaultRole`, the `isDefault` strip at the mint/patch funnels), `server/model/tools.ts` (`create_agent` / `commission_agent` resolve before the card), `contract/providers.ts` (`defaultEntry`), `contract/cowork.ts` (`Project.defaultRole`) | instance locks: `server/routes/registry-defaults.test.ts`, `server/routes/worker-agents.test.ts`, `server/routes/commission.test.ts`, `server/model/model-tools.test.ts`, `tests/consent-state.test.ts`; the general classification of each NEW field is review-enforced (no automated guard for fields not yet written) | ✅ |

| INV-11 | **Access parity — every access interface is equally capable and gated by the same policies.** The product has three access methods — the browser **UI** (a client of the HTTP API), the **in-app session** (the model serving a conversation), and the **MCP door** (`/mcp`, PORT-9) — and they may differ in *form* but never in capability or in the authentication/authorization that gates them. The rule is held **by construction, at the funnel**, not by review: there is ONE route table (the router), ONE operation catalog derived from it (`server/apiSurface.ts`), ONE identity resolution (`server/identity.ts` — the same signed session credential over cookie or bearer), and ONE wall (the router middleware: auth gate, tenancy, idempotency, limits). Both non-HTTP doors GENERATE their tool surface from that catalog and re-enter the router for every act — the MCP door per tools/call with the caller's own credential; the in-app session per generated API tool (MODEL-25: reads run as the sending user; mutations become family-carded proposals executed as the CONFIRMER) — and neither contains authorization logic of its own; an access method that grew a private policy branch would be the regression this invariant names. The only gaps are ARGUED, never silent: stream-shaped routes (form — `MCP_EXCLUDED`), and the model leg's three excluded planes (`MODEL_API_EXCLUDED`: the conversation plane, the identity/credential plane, machine self-service edges — the model must never confirm its own proposals or handle credentials). | `server/apiSurface.ts`, `server/http/dispatch.ts`, `server/mcp.ts`, `server/model/apiTools.ts`, `server/identity.ts`, `server/routes/index.ts` (the middleware wall) | `server/mcp-parity.test.ts` (bijection + wall parity), `server/model/api-tools.test.ts` (the in-app leg), `server/routes/auth-bearer.test.ts` (one credential, two transports), `server/mcp.test.ts` | ✅ |
| INV-12 | **The solid-fill seat — text on a fill is legible on that fill, in every palette and both modes** (UI-20, [`docs/ui-invariants.md`](../ui-invariants.md)). Refines INV-1: token theming alone does not make a pairing legible. A colour that is READ (accent-as-text on the canvas, `*-strong` as emphasis copy) and a colour that is FILLED UNDER TEXT are different jobs, and dark mode LIGHTENS the accent so it reads on a dark ground — which is exactly what stops it carrying white. So a fill under `text-on-solid` wears its own `--color-*-solid(-strong)` seat, while `accent` / `*-strong` keep the text/dot/bar role. Every seat clears WCAG AA **4.5:1** against `--color-on-solid` across all four palettes × both modes; the text seat is separately held to 3:1 against the canvas, so the two cannot be collapsed back together by darkening the accent until it passes. The only exemption is an IMAGE backdrop (a photo scrim, generated cover art), enumerated and alive-checked. Earned by the palette axis shipping the CTA at 1.74:1 (Forest dark hover), with the status pills failing in light mode too. | `src/index.css` (the `*-solid` family), `src/lib/theme.ts` (`PALETTE_TOKENS`), `src/lib/button.ts`, `src/lib/checkbox.ts` | `tests/contrast.test.ts` (the palette × mode × seat matrix, seat list derived from the stylesheet; the tree-wide `text-on-solid` call-site scan; the banned text-tuned fills; a self-check of the ratio maths) | ✅ |
