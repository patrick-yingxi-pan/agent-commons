# Recognizing a task partner

Two providers called **Orchard Services** can both be legitimate. A requester looking for the provider at `orchard.example` should be able to find it by that address. A saved task should keep using the same provider even if a second organization adopts its name. The partner registry gives people a verified website to recognize, binds permissions to a permanent partner ID, and gives visitors a first-party page where they can check a website badge. [Integration guide](task-partner-integrations.md) · [Web flows](task-partner-web.md) · [OpenAPI contract](task-partner-api.openapi.json)

## Establish the public identity

Agent Commons assigns a permanent, opaque partner ID. A production organization has one canonical profile on the configured Agent Commons web origin at `/partners/{partnerId}`. Display names can change and need not be unique. The profile shows the exact verified website host, the organization's current status and the capabilities approved in production. A badge can therefore say **Approved reward custodian · orchard.example**. Domain control alone does not establish trademark ownership, legal identity, or the safety of everything on that website.

| Event | Automatic decision |
| --- | --- |
| Apply | Parse the proposed HTTPS website and handoff hosts using one IDNA policy. Store their lowercase ASCII DNS forms. Reject credentials in URLs, IP literals, local hosts and public suffixes. Treat an apex, `www` and other subdomains as distinct. Only an exact approved origin may display the live mark. |
| Prove control | Issue a fresh, unpredictable DNS TXT challenge at `_agentcommons.<host>`, bound to the application, environment, host and purpose. The partner's DNS automation publishes the record. The site resolves it independently and records the proof. Complete the key-possession and capability checks separately. An applicant's URL, email address or logo cannot satisfy the DNS challenge. |
| Activate | In one transaction, enforce unique ownership of the canonical primary host among live production bindings, store its identity revision, and publish the approved profile. A concurrent application for the same host cannot overwrite it. Organizations operating at different paths on one shared host need distinct verified hosts to receive distinct website badges. |
| Renew | Allow 24 hours to answer a challenge. Cap a proof lease at 30 days, recheck the proof at least daily, and issue a fresh challenge before expiry so renewal can run unattended. Scope the partner's DNS automation to the challenge record. A failed lookup never extends a lease. Once proof is stale or control is contradicted, suppress the positive badge and new authorizations. |
| Change, lapse or revoke | Prove a replacement host before switching it. Increment the identity revision for a changed binding, disable old-site badges, and recheck consent before new work. Keep the permanent profile accessible with truthful status after lapse, suspension or revocation. Retain the ID, domain and issuer recorded on earlier evidence. An expired proof, transferred domain or renamed organization cannot inherit someone else's pins, signatures, holds or history. |

Use a versioned Public Suffix List, including its private-domain rules, to identify registrable domains for display and to reject shared suffixes as identity claims. Keep the full verified host visible, with the registrable portion legible. For internationalized hosts, also expose the ASCII A-label that the service actually verified. Render names as isolated text and disallow user-supplied directional override controls. The UI supplies its own direction and layout. [Unicode IDNA processing](https://www.unicode.org/reports/tr46/tr46-35.html) · [Public Suffix List](https://publicsuffix.org/list/)

## Detect names a person might confuse

Compare a proposed or changed display name against other partner identities before it becomes selectable. Keep the entered name for display. Compute the following independent lookup data using a pinned Unicode release. The protocol fixtures use **Unicode 17.0.0**.

1. Check exact equality, then compare Unicode NFKC case-folded names with whitespace and punctuation removed. This catches capitalization, width, spacing and punctuation variants.
2. Compare UTS #39 confusable skeletons of those normalized names. This catches visually similar characters within and across scripts. Use the full versioned Unicode tables and bidirectional processing. A skeleton is internal comparison data.
3. Compare the normalized code points for small edits, including adjacent transpositions. The initial policy uses optimal string alignment distance of at most one when the shorter name has at least five code points, or at most two when it has at least twelve. Shorter names still receive exact, normalized and skeleton checks.
4. Check distinct canonical domains for visually confusable Unicode host forms, preserving label boundaries and suffixes. Domain comparison for **authorization** always uses the exact ASCII host. A similarity match can never grant domain control.

The directory, task selector, consent screen, public profile and website badge use the same three labels. **Identical name** means another published partner uses the exact display name. **Similar name** covers normalized, visually confusable and near-match names. **Similar website domain** means two distinct verified domains can look alike. Show every applicable label alongside the full ASCII host. A domain-only match shows only the website label.

Compute the strongest name signal for each pair and the domain signal when applicable. The public profile summarizes those signals and links to related published partners. Show peers side by side with their domains. For example, a directory search for “Orchard Services” can show two exact names and also flag “Orchard Servcies,” while an exact-domain lookup of `orchard.example` selects just its bound ID. Show the same context on both profiles. A new applicant gains no priority over an existing partner by triggering a collision. Keep unpublished applicants and their contacts out of public comparison results.

Index the exact, normalized and skeleton keys; use an indexed, length-bounded candidate search for edit distance and verify candidates with the stated rule. Recompute affected peers on publication, rename or status change. Stage a full index rebuild before changing Unicode or matching-policy versions. If the index is unavailable or out of date, allow exact-domain or pinned-ID resolution while withholding name-only selection for a new sensitive action. [Unicode security mechanisms](https://www.unicode.org/reports/tr39/tr39-32.html) · [Pinned confusables data](https://www.unicode.org/Public/17.0.0/security/confusables.txt)

## Resolve the intended party before authorization

Search results are for discovery. Display **name + exact domain + approved role** in results, task terms, sign-in handoffs and custody details. An ambiguous search has no default selection. Before a first grant to an ambiguous partner, use an existing trusted partner pin or ask for the exact domain obtained independently, for example from the requester's own supplier configuration. Do not prefill that answer from the search result. Two different sites can each prove control of their own domain; a name matcher cannot determine which supplier the requester intended.

The server checks the expected domain, identity revision, partner ID, active status and required capability when starting a handoff, confirming it and dispatching new work. UI and MCP use the same checks. Save the resulting binding for later use. A new lookalike or routine signing-key rotation does not invalidate an existing binding. A changed domain or lost capability requires a fresh decision for new work. An unpaid task without a partner needs none of these steps.

Ordinary overlap is handled by the registry and interfaces without a moderation queue. Escalate conflicting ownership of the same host, disputed transfers or evidence of a compromised binding through the existing incident process. Preserve the original task's recovery path for outstanding rewards.

## Publish the website badge

After production approval and current domain proof, the partner console offers a copyable HTML embed and a plain profile link. The embed loads a small, script-free frame from Agent Commons' badge origin. It displays the verified host and approved role and opens the permanent organization page on the Agent Commons web origin. The organization page can link visitors back to the exact verified website. The OpenAPI examples provide the literal HTML, destination and response headers. [Badge examples](task-partner-api.openapi.json)

For each badge request, the service loads the public production identity, checks its status, capability and exact requested host, and derives the destination from the trusted web origin and stored ID. Its HTTP `Content-Security-Policy: frame-ancestors` allows only the verified HTTPS origin for that embed. Browsers enforce this for **every** ancestor. Copying an embed to another host or nesting it through an approved host cannot display the active frame there. The badge service uses no account cookies, scripts or visitor-specific tokens. Responses use `Cache-Control: no-store`; recheck status on each load and on every visit to the canonical profile. [CSP frame ancestor enforcement](https://www.w3.org/TR/CSP3/#directive-frame-ancestors)

A publisher can still draw a lookalike badge or copy a screenshot. Visitors can check the Agent Commons origin, approved capabilities, domain and status on the destination page. The profile never treats a referrer, a badge click or a query-string return address as proof of the referring site's identity. An old open tab can retain previously painted pixels; new authorizations always read current registry state.
