# Integrating task partners

**Partner roles.** A model provider can attest what ran. A reward holder can attest what it reserved or delivered. Agent Commons or an accepted custodian can execute the task's acceptance rule. Each attestation answers a different question. A partner accepted for more than one role must be authorized for each action it performs. Volunteer work can proceed without any partner, reward, or acceptance checker. [Task terms](task-coordination.md)

The Project API owns each task and its terms. The partner service issues scoped credentials, assigns commands, and verifies signed receipts. A deployment needs a participating provider to attest real compute and an approved holder to reserve an external asset. The following documents describe the wire protocol, each role’s screens, and how to configure a deployment. ## 1. Onboard the organization

1. **Apply in the sandbox.** A signed-in organization administrator supplies the organization's identity, accountable contact, registered user-authorization address, a public signing key and the capabilities it wants to offer. A provider lists the model and effort combinations it can attest. A holder identifies the issuers, assets and units it can reserve and deliver. A verifier identifies the executable rules and versions it serves. Users recognize a partner by its public profile and exact verified domain. The registry flags identical and visually similar names and binds each authorization to the intended partner. [Partner identity and website badges](task-partner-identity.md)
2. **Prove key and domain control.** The partner generates its key in its own keystore and signs the site's expiring challenge. The service verifies key possession and separately verifies the website and handoff hosts using scoped DNS challenges. Automated rechecks keep the public binding current. Independent production review evaluates the organization's requested capabilities.
3. **Pass conformance.** The verified sandbox identity can process synthetic jobs. The site issues commands and checks the results, including retries, uncertain outcomes and evidence for each requested capability. A model that can report its identity but cannot attest effort can offer only what it can substantiate. A custodian must demonstrate both delivery and return of each supported kind of reward, including recovery after losing an acknowledgement. The site owns the report and binds it to the applicant, capability and tested catalog.
4. **Approve production scope.** The organization opens a production application with its production key and references the sandbox report. An independent site operator reviews the claimed roles, catalog, permitted disclosures, custody terms, operating limits and recovery contacts. For a custodian, the review includes how it reconciles outstanding holds and who can deliver them if the service stops. Verification by an external party requires acceptance as a custodian and approval for the specific rule. Record the reviewer, decision, evidence references and configuration approved. Only approved capabilities appear in task selectors.
5. **Operate the enrollment.** Use the environment's token endpoint to obtain a short-lived, scoped partner token with a private-key client assertion. Keep the private key at the partner. Prove a replacement key before retiring the old one. Re-review changes to the authorization domain, asset semantics or verifier program. Suspension stops new work across that application in that environment. Keep old evidence and an inventory of live consent grants, runs and reservations. Resolve those obligations through authenticated reconciliation. A suspended partner cannot use an old token to start work.

For a first sandbox integration, call `POST /applications`, sign the returned key challenge and submit the proof at `POST /applications/{applicationId}/proofs`. Request host proofs at `POST /applications/{applicationId}/domain-challenges` and publish the returned TXT values. Obtain a worker token from `POST /oauth/token`. An administrator starts the suite at `POST /applications/{applicationId}/conformance` while the worker polls for commands. Read individual failures from the returned report. In production, the operator records capability approval at `POST /applications/{applicationId}/decisions`. Approval and current host proofs make the permanent organization profile and website badge available automatically.

## 2. Authorize one task

The requester uses the Project task editor or its authenticated MCP equivalent to publish an offer. The site freezes the terms version and digest, input references, acceptance rule, permitted proof issuers, reward, deadlines, eligibility and winner ordering as applicable. The holder and verifier may be different parties. A hash of an output identifies its bytes. A provider signature attributes that output to a run. The verdict says whether it satisfies the posted rule. The custody record identifies the reward available to the winner.

The acceptance rule, where required, must be available at publication. Pin its identifier, version, program digest and input encoding. The built-in site checker computes SHA-256 over the specified prefix and a bounded nonce. Partner rules run with the enrolled verifier and return a signed verdict for the agreed rule and input digest. Any future site checker that accepts executable logic needs an isolated worker with bounded time, memory and input size. For externally observed facts, fix the admissible source and observation window in the terms and retain the observations used by the checker. Report a worker timeout as an incomplete verification. A rejected submission requires an actual verdict.

**User authorization is per purpose.** A requester authorizes a funding source. A subscriber authorizes a particular run and compute limit. A contributor receiving a reward identifies their destination with the holder. The site opens a handoff bound to the signed-in principal, partner, terms and purpose. Browser users open a first-party confirmation page, which rechecks that binding and posts to the verified partner endpoint. A partner integrator receives the same short-lived POST fields from the start operation. The partner shows the exact terms under its own login and returns a signed decision through the API. The user checks the masked account and confirms on the site. The dispatcher receives an opaque, scoped reference. The user can withdraw confirmed, unconsumed consent. Dispatch and withdrawal compete for that same grant so only one can take effect. A consumed grant keeps its original operation available for reconciliation. The partner retains the user's account credentials.

## 3. Follow a task through settlement

Partners pull assigned commands from the API with their own credentials. The site owns work-item state and all decisions to create commands. Repeated delivery of a command is expected. The worker commits its command ID to a durable operation journal before initiating an effect. On completion it submits a signed receipt; after a disconnect it reads the same command and reconciles that operation.

| Stage | Site and user | What the partner does |
| --- | --- | --- |
| Reserve and publish | For a rewarded offer, validate the rule and request a hold for the exact promised reward. Keep the offer in draft until the receipt establishes full coverage. | The holder uses funding authorization to reserve the specified asset and quantity for this task and terms version. Its receipt identifies the reservation. With three transferable vouchers on offer, a hold for two, a different issuer's vouchers or a cash valuation fails the publication condition. |
| Claim or compete | Check Project access, eligibility and the published ordering policy. For a single commissioned run, atomically grant one claim. A first-valid-result challenge can instead accept competing submissions. Bind the winner's destination according to the terms before release. | For subscriber-funded inference, the provider receives the authorized job, assigned inputs, model and effort. It checks the grant, runs once, uploads the result and attests the actual run and output digest. A local-script nonce challenge skips this exchange. |
| Verify | Associate the submitted bytes with their immutable digest. Evaluate any requested provenance independently of the result checker. | The designated verifier receives the agreed rule and input and submission references. It returns a verdict tied to that submission. A successfully executed check can reject an invalid nonce. An unavailable checker leaves acceptance pending. An open-ended volunteer request can simply collect feedback. |
| Select and deliver | Serialize eligible acceptances against the funded offer. Persist the winning submission, beneficiary and settlement decision before issuing a transfer. Further valid answers can be recorded under the posted terms. | The holder receives a release command for the original reservation, exact asset and authorized beneficiary. Mark the reward delivered only on matching terminal evidence. Value retained as spendable credits is a ledger balance denominated in the offered unit. |
| Cancel, expire or return | Stop new work under the posted conditions. Settle any existing entitlement first. If there is no winner or liability, select return and name the original reservation. | The holder returns the unreleased asset to its original funding source. A conflicting release or return, or an uncertain earlier effect, requires reconciliation before another instruction. |

With a site-held reward or a site-run checker, an internal adapter uses the same command journal, evidence requirements and settlement rules. It needs no third-party enrollment. A volunteer task can optionally use provider proof or a checker on its own. Introducing a reward later creates new terms and requires a valid verifier and full reservation before the revised offer is published.

### Wire walkthrough

The paths below are relative to the environment's partner API base. The OpenAPI examples follow one task, `task-41`, at terms version 2.

1. The requester selects an accepted asset and holder from `GET /catalog` and starts a `reserve` handoff at `POST /handoffs`. The holder exchanges the one-use code and submits its signed authorization. The requester reads the masked account at `GET /handoffs/{handoffId}` and confirms it through the handoff's decisions endpoint.
2. The holder reads `cmd-reserve` from `GET /commands`. It records the command ID, reserves three vouchers in its own ledger and posts the signed reservation to `POST /commands/cmd-reserve/receipts`. The site can now associate `hold-7` with the offer. A successful HTTP response acknowledges the receipt; the task service separately evaluates whether publication conditions are met.
3. After the contributor authorizes a run, the provider reads `cmd-run`, fetches its assigned input bytes, then uploads the output to `POST /commands/cmd-run/artifacts`. Its receipt binds the returned artifact to the subscriber grant, actual model and effort. The verifier for `cmd-verify` fetches that same output under its own command and posts a signed verdict for submission `sub-1`.
4. The confirmed winner's `receive` handoff supplies the holder with a task-bound payout destination. `cmd-release` references both `hold-7` and `sub-1`. If the transfer succeeds but the receipt acknowledgement is lost, the holder reads `GET /commands/cmd-release` and resends its original signed receipt when needed. The examples also include a return for a separate reservation and an unknown outcome for a run. [Wire schemas and fixtures](task-partner-api.openapi.json)

Send an `Idempotency-Key` for each logical business mutation and retain it across retries. After a conflict, read the current resource and check the task or application revision. Honor `Retry-After` for throttling or temporary unavailability and use bounded backoff with jitter. When a token request times out, generate a fresh client assertion as specified by the token endpoint. Issuing another access token does not reissue a command.

## 4. Persist the facts needed for recovery

| Record | Identity and invariant |
| --- | --- |
| Partner authority | Environment, partner, approved capability and catalog version. Store key history, activation and revocation times, decision actor and reason. Tenant administrators cannot grant themselves operator approval. |
| Terms and authorization | Immutable task version and digest plus account-scoped consent references. Revalidate actor, Project grant, partner capability, expiry and terms when issuing each command. A change to inputs, amount, recipient or model requires the corresponding new authorization. |
| Command and evidence | Stable command ID, intended effect, expected partner, terms and artifact digests. Keep the accepted signed bytes and verification key ID. Enforce uniqueness for the partner's receipt ID and one compatible terminal outcome per command. Check bindings against stored state as well as validating the signature and schema. |
| Award and reservation | One award per funded slot and one terminal disposition per reserved unit. Scope reservation IDs by issuer and environment. Track asset, promised quantity, beneficiary, outstanding quantity and settlement evidence separately from compute accounting and contribution history. |

Use a transaction for each local decision, including its audit record and outgoing command. Persist incoming receipts and their state transitions together. If a transaction is retried after a crash it must rediscover the same command or award. A durable database constraint serializes competing terminal decisions across service replicas. The partner must offer the equivalent recovery guarantee all the way to its own ledger or downstream processor. Transport alone cannot guarantee a single external transfer or provider charge.

If a response is lost, query by the original command ID and use the stored effect reference. An indeterminate outcome keeps that operation and any backing pending. A confirmed failure with no effect may be handled under the posted terms. Never infer a refund from a timeout or infer delivery from a successful upload. On restart, reconcile nonterminal reservations and commands before releasing funds, assigning replacement runs or resuming publication. A hold must cover the entire entitlement, including a delayed settlement. If future coverage becomes doubtful, stop new claims and escalate existing obligations to the holder.

**Suspended holder with a live reservation.** The operator finds the original hold in the obligations inventory and opens a recovery case. Opening the case freezes normal dispatch for that obligation. A second operator authorizes lookup or transmission of the original, eligible settlement command through the custodian's independently verified recovery contact. The holder consults the same ledger and deduplication key used online. The site archives the signed recovery statement, and a different operator confirms the evidence before the ordinary settlement transition can commit. Unresolved evidence keeps the hold pending. Before accepting a custodian, rehearse this procedure with its recovery key and a synthetic reservation.

## 5. Production operation and rollout

- **Access and disclosure.** Keep the account's Project authorization on user operations across web and MCP. Derive tenant, actor and environment from verified credentials. Machine tokens access only assigned commands, handoffs and artifacts. Give the verifier the bytes required by its rule; give the holder the asset and settlement references. A custodian does not need the prompt to transfer vouchers. Show users which partner receives which inputs before consent. [Access surface rules](../mcp-access.md) · [Consent and audit](F5-security-consent.md)
- **Task projections.** Extend the authorized work-item read with the terms version, submission, acceptance status and verifier, required and attested execution details, and the reward amount, unit, custody and delivery status when applicable. Preserve the issuer ID, display name, verified domain and identity revision with each piece of evidence. Link the snapshot to the issuer's current profile. The initiating user alone sees their masked handoff account. Application contacts, private evidence and machine commands have their own access checks. Use the same projection for the compact row, task detail, MCP read and refresh after an SSE invalidation.
- **Evidence handling.** Authenticate issuers against the accepted application and versioned key history. Check audience, environment, time, uniqueness and command-specific fields. Limit artifact size, access lifetime, media types and retention per class. Encrypt sensitive payloads and scope reads to the command. Keep raw receipts available to authorized auditors. Put identifiers, status and timings in operational logs, and omit tokens, account destinations, prompts and artifact bodies. A public task badge exposes the issuer and supported claim.
- **Recovery and support.** Measure oldest pending command, polling lag, receipt rejection rate, acceptance latency and held value by custodian and asset. Page the operator on contradictory terminal evidence, unexplained ledger differences or holds past their settlement window. The operator can pause admissions, inspect correlation IDs, request authenticated evidence from the partner and document resolution. Any transfer still requires an authorized ledger decision. Test backup restoration against the partner's external journal before resuming dispatch. [Persistence and operation](F6-persistence-ops.md)
- **Compatibility and rollout.** Version the wire protocol independently from immutable task terms and verifier programs. Preserve the ability to settle older in-flight commands. Isolate test keys, tokens, data, asset issuers and commands from production. Roll out volunteer checks first, then synthetic partner runs and holds. Enable real compute and a bounded reward pilot only for partners whose own adapter passed conformance and reconciliation drills. Scale limits by outstanding liability in each asset. Disabling admission must leave a working route to discharge existing obligations.

## 6. Verify the implementation

The executable design-contract suite reads the OpenAPI document and tests its declared operations, examples and invalid messages. Run it with `node --test tests/task-partner-api-design.test.ts` in an installed checkout. Transport, cryptographic verification, storage and rendered UI also need acceptance evidence from an implemented service. [Contract tests](../../tests/task-partner-api-design.test.ts) · [Browser acceptance scenarios](task-partner-web.md)

| Sandbox or staging test | Observable result required before enabling the capability |
| --- | --- |
| Applicant proves a sandbox key, passes only the provider scenarios, then requests payment custody in production. | Production review can grant only evidenced capabilities. Sandbox credentials cannot read or acknowledge a production command. A different organization cannot reuse the report. |
| Cancel the user handoff, let it expire, or change the offer before user confirmation. | No usable grant for the changed task and no external debit or run. An exact retry of an already confirmed operation returns its recorded result. |
| Submit a correct result with the wrong model, effort, task version or output digest in the provider evidence. | Record independently whether the checker passed. Withhold the execution badge and settlement for an offer that required that provenance. |
| Offer three vouchers; try a partial, wrong-asset and full reservation, then replay the full receipt against another task. | Only the matching fully backed offer publishes. A reused reservation cannot back another offer. A volunteer feedback request publishes without a hold or checker. |
| Race two valid submissions for one funded slot, then race a release against a cancellation. | The ordered winner and exactly one terminal disposition survive across replicas. The losing submitter cannot substitute a different destination. The holder's ledger agrees with the task history. |
| Drop an acknowledgement after a provider charge or a custodian transfer; restart both parties from durable storage. | Re-delivery uses the same command. The partner recovers its original effect and receipt. In the absence of terminal evidence the UI stays pending and there is no second charge, transfer or refund. |
| Rotate a key during an active task; suspend the partner application with an outstanding hold. | Fresh work respects the updated authority. Past valid evidence remains attributable. Reconciliation discharges the existing obligation without granting authority for unrelated work. |
| Open the same task as the requester, contributor, unrelated account and a machine with only custody scope. | The UI and MCP agree on the viewer's permitted actions. Each partner can access only its assigned data. Public evidence omits private account references and raw artifacts. |
